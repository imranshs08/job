AGIC to AGC Migration Guide

Azure Application Gateway for Containers
🟢 Production-Ready (Replaces AGIC)

🏗️ Architectural Differences: AGIC vs. AGC

For a long time, the standard Layer 7 ingress for AKS was the Application Gateway Ingress Controller (AGIC). However, AGIC suffered from architectural limitations (specifically translating configurations into slow Azure ARM API calls).

Application Gateway for Containers (AGC/ALB) was built from the ground up for Kubernetes. It is the designated evolution and replacement for AGIC.

Feature Legacy AGIC New AGC
Control Plane Relied on Azure ARM API (slow) Dedicated ALB Controller (near real-time)
Kubernetes APIs Standard Ingress only Supports both Ingress and the Gateway API
Deploy Time Minutes (often 5+ min) Milliseconds
Routing Clunky via annotations Weight-based routing natively via Gateway API

⚠️ Azure Application Routing Add-on

Important Distinction: The Application Routing Add-on is not Application Gateway for Containers.

The Application Routing Add-on is a fully managed NGINX Ingress Controller running inside your AKS cluster as Pods.

  • Use AGC when: You want a heavy, scalable Layer 7 load balancer outside your cluster (offloads compute).
  • Use App Routing when: You want a fast, simple, in-cluster NGINX setup for dev/test or internal traffic, with auto-Key Vault integration.

🚀 4-Phase Migration Strategy (Zero-Downtime)

Microsoft recommends a side-by-side coexistence strategy. You do not need to delete AGIC to start using AGC.

Phase 1: Preparation & Deployment

  1. Deploy the new ALB controller in your AKS cluster.
  2. Provision the AGC Resources (Frontend, Subnet association) in Azure.
  3. Review existing Ingress YAMLs and map AGIC annotations (appgw.ingress.kubernetes.io/*) to ALB annotations (alb.ingress.azure.com/*) or modern HTTPRoute resources.

Phase 2: Coexistence & Validation

  1. Deploy a duplicate Ingress/HTTPRoute targeting the exact same internal Pods, but using the alb ingress class.
  2. Traffic to the old public IP remains untouched on AGIC.
  3. Access the new public IP generated by AGC to validate routing and SSL.

Phase 3: Cutover using DNS

  1. Update public DNS (e.g., Azure DNS, Cloudflare) to point your domain from the old AGIC IP to the new AGC IP.
  2. Monitor telemetry for 200 OKs.

Phase 4: Decommission

  1. Delete the legacy AGIC Ingress resources.
  2. Delete the legacy App Gateway v2 resource to save cloud costs.
