# Azure Application Gateway for Containers (AGC) — Technical Overview & Migration Strategy

> **Status:** Production-Ready (Replaces AGIC)  
> **Ecosystem:** Azure Kubernetes Service (AKS), Gateway API, ALB  

For a long time, the standard Layer 7 ingress for Azure Kubernetes Service was the **Application Gateway Ingress Controller (AGIC)**. However, AGIC suffered from architectural limitations — specifically, translating Kubernetes configurations into slow Azure ARM API calls, leading to deployment delays of 5–15 minutes on large clusters.

To solve this, Microsoft built **Application Gateway for Containers (AGC/ALB)** from the ground up for Kubernetes. It is the designated evolution and replacement for AGIC.

---

## 1. Architectural Differences: AGIC vs. AGC

| Feature | Legacy AGIC | Application Gateway for Containers (AGC) |
| :--- | :--- | :--- |
| **Control Plane** | Relied on Azure ARM API (slow). | Uses a dedicated ALB Controller (near real-time). |
| **Kubernetes APIs** | Standard `Ingress` only. | Supports both `Ingress` and the modern **[Gateway API](https://gateway-api.sigs.k8s.io/)**. |
| **Deployment Time** | Minutes (often 5+ min). | Milliseconds (updates apply instantly). |
| **Traffic Splitting** | Clunky, via annotations. | Native Weight-based routing using Gateway API. |
| **Deployment Model** | Paired 1-to-1 with an App Gateway v2. | Decoupled; one AGC can handle multiple clusters. |

---

## 2. The Application Routing Add-on (The Alternative)

While AGC is the direct replacement for enterprise Layer 7 offloading, Microsoft also introduced the **Application Routing Add-on**. 

> ⚠️ **Common Misconception:** The Application Routing Add-on is *not* Application Gateway for Containers. 

The Application Routing Add-on is a fully managed **NGINX Ingress Controller** running *inside* your AKS cluster as Pods. 
- **Use AGC when:** You want a heavy, scalable Layer 7 load balancer *outside* your cluster (offloading CPU/Memory).
- **Use App Routing when:** You want a fast, simple, in-cluster NGINX setup for dev/test or internal traffic, with auto-Key Vault integration.

## 3. Production Migration Strategy (AGIC to AGC)

Microsoft recommends a **Zero-Downtime Coexistence Strategy**. You do not need to delete AGIC to start using AGC; they can run side-by-side in the same cluster.

### Phase 1: Preparation & Deployment
1. **Enable the ALB Controller:** Deploy the new ALB controller in your AKS cluster (via Helm or AKS Add-on).
2. **Provision AGC Resources:** Create the Application Gateway for Containers, Frontend, and Subnet association in Azure.
3. **Map Annotations:** Review your existing `Ingress` YAML files. If you use AGIC-specific annotations (`appgw.ingress.kubernetes.io/*`), translate them to ALB annotations (`alb.ingress.azure.com/*`) or adopt the native Gateway API `HTTPRoute` resources.

### Phase 2: Coexistence & Validation (Canary Testing)
1. Deploy a duplicate `Ingress` or `HTTPRoute` resource targeting the exact same internal Kubernetes Pods/Services, but specifying the `alb` ingress class instead of `azure/application-gateway`.
2. Traffic to the old public IP remains on AGIC.
3. Access the *new* public IP generated by AGC to validate that routing, SSL, and traffic splitting work as expected.

### Phase 3: Cutover using DNS
1. Once validated, update your public DNS (e.g., Azure DNS, Cloudflare) to point your domain (`api.yourcompany.com`) from the old AGIC IP to the new AGC Frontend IP.
2. Monitor telemetry (Azure Monitor/Log Analytics) to ensure 200 OKs.

### Phase 4: Decommission
1. Delete the legacy AGIC `Ingress` resources.
2. Delete the legacy Application Gateway v2 resource to save cloud costs.

> 🛠 **Automation Tool:** Microsoft provides an open-source **[AGC Migration Utility](https://github.com/Azure/Application-Gateway-for-Containers-Migration-Utility)** on GitHub to help auto-convert your YAML manifests.
